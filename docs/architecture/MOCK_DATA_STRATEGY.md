# Mock Data Strategy

Everything astrological in this application is illustrative fixture content. Nothing is calculated from an ephemeris, no reading is generated by a model, and no astrology or interpretation service is connected.

This document exists so that nobody later mistakes any of it for a calculation.

## What is mocked

| Surface | What it really is |
|---|---|
| Daily readings | Twelve authored fixtures, one per Sun sign, each holding a Normal and a Roast register |
| Precise readings | Authored prose that names mechanics — a house ingress, a retrograde shadow clearing — none of which were computed |
| Sign profile | Sun sign from fixed calendar boundaries; sidereal rashi by stepping back one division; year pillar from the sexagenary cycle offset |
| Charts | Positions spread deterministically from the birth date so a given person always sees the same chart. Not an ephemeris |
| Aspects | Computed from those fake positions with a fixed six-degree orb |
| Sky | Sun and Moon longitudes from a circular-orbit toy model; phase derived from their elongation |
| Compatibility | Verdicts selected by element and modality relationship; prose from a fixture bank |
| Ask | Answers chosen from a fixture bank by keyword. No model is involved |
| Glossary | Editorial definitions |
| Circle | Two seeded people so the feature is visible without setup |

`MockAstrology` computes rather than hard-codes, for one reason: a screen reading "waxing gibbous, 88% illuminated" beside a sentence about a new moon is not placeholder content, it is visibly incoherent, and incoherence in a product whose whole promise is showing its reasoning reads as carelessness. Deriving everything from one date keeps each screen internally consistent while remaining openly fake.

**None of it is accurate.** It ignores the year, the hour, the observer's location, precession, orbital eccentricity and every calendar convention a real implementation must resolve. Do not port any of it into a calculation layer and do not use it as a test oracle.

## Four independent guards

1. **Type.** Every content-bearing domain value carries a non-optional `ContentProvenance`. Mock services emit `.mockFixture(fixtureID:)`. `.calculated` exists but has no producer.
2. **Construction.** `MockContentProvider.provenance(_:)` is the only way to build a provenance inside `Data/Mock/`. No mock file writes `.mockFixture(fixtureID:)` literally, so a value cannot escape the layer unmarked.
3. **Runtime.** In DEBUG a `SAMPLE` kicker renders beside any basis line whose provenance is mock, so a screenshot cannot be mistaken for a real reading.
4. **Process.** `Scripts/check-layering.sh` fails if `Presentation/` names a concrete `Mock*` type. Every file in `Data/Mock/` opens with a boundary banner.

Methodology-blocked values are withheld rather than filled in: the BaZi Luck Cycle ships as `FactValue.unavailable(.methodologyPending("METHOD-006"))`, and the Vedic ayanamsa and BaZi calendar conventions are stated on screen as unsettled development defaults.

## Where it lives

```
Humay/Data/Mock/
├── MockContentBoundary.swift        marker protocol, provenance factory, latency
├── MockAstrology.swift              the toy model — not astronomy
├── Mock*Service.swift               one per service protocol
└── Fixtures/
    ├── DailyReadingFixtures.swift   12 signs x 2 registers, one shared basis each
    ├── PreciseReadingFixtures.swift
    ├── ChartFixtures.swift          sign profile, Western/Vedic/Chinese prose, placement detail
    ├── CompatibilityFixtures.swift
    ├── SkyFixtures.swift
    ├── AskFixtures.swift
    └── SeedCircleFixtures.swift
```

Fixtures are Swift rather than JSON. They are type-checked, they cannot fail to decode at runtime, and they need no loader — which matters because the whole directory is deleted rather than migrated when real services arrive.

## The tone invariant

A fixture holds both registers and one basis. `MockHoroscopeService` picks a register and reads the basis from the shared parent, so there is no code path in which choosing Roast changes the reasoning. `ToneInvarianceTests` asserts it across all twelve signs.

## Simulated latency

`MockLatency.realistic` (180–520 ms) in the application, `.instant` in previews and tests. Loading states are therefore exercised on device without slowing the suite.

## Replacing it

`AppEnvironment+Live` is the only file that names a `Mock*` type. When real services arrive:

1. Implement the same protocols in a new `Data/Remote/` layer.
2. Change `AppEnvironment.live()`.
3. Delete `Humay/Data/Mock/` entirely.

`Data/Mock/` is **replaced, not extended**. That is the exit condition on `DEV-001`.

Service protocols are already `async throws` and shaped for what a real implementation needs — `AstrologyAssistantService.answer` takes the whole conversation and returns a message carrying its own basis, so a provider-backed version needs no signature change.
